OpenSpec design · theme-ai-palette-suggest

Design: AI-suggested palette in the theme editor

Add a “Suggest with AI” button to the existing custom-theme editor that calls a local Ollama model to propose a starting 4-color palette for the current song — a human-in-the-loop assist, not an unattended generation-pipeline decision.

Session findings (manual testing, 2026-08-02)

ApproachResult
format: "json" (string)Unreliable — valid-but-inconsistent shapes: {"colors":[...]}, {"colorPalette":...}, {"$colorPalette":...}, malformed duplicate keys, once a literal echoed JSON Schema instead of data
format: <JSON Schema> (structured output)10/10 clean bare 4-item hex arrays across 2 runs × 5 songs, 1.2–3.6s/call, zero malformed output, zero timeouts
Longer, guideline-heavy promptMade output worse on an 8B model — degenerate repetition, broken JSON
llamusic/llamusic:3b (music-specialized)Unreliable JSON despite domain specialization
gpt-oss:20b (reasoning model)Too slow / only emitted reasoning preamble, even with think: false
qwen3:8b + schema formatWinner — fast, reliable, plausible (not always highly differentiated) palettes

Quality caveat: outputs lean on a handful of go-to colors (gold #FFD700, purple #8A2BE2) across many genres rather than deeply differentiating every song. Decent starting point, not a finished always-novel palette — the reason this belongs in the existing manual editor, reviewed by a human, not an unattended pipeline step.

Approach

Backend

src/review/ai_palette.py::suggest_palette()

def suggest_palette(
    title: str, artist: str, genre: str, occasion: str,
    ollama_host: str, ollama_model: str, timeout_s: float = 10.0,
) -> list[str] | None:
    ...

stdlib urllib.request only (no new dependency). Short validated prompt + JSON-Schema format (array, exactly 4 items, ^#[0-9A-Fa-f]{6}$ pattern). Defensive re-validation of the response even though schema-constrained. Returns None on any failure — connection refused, timeout, malformed JSON, wrong shape — never raises.

Backend

New route + settings keys

POST /api/v1/songs/<song_id>/theme-suggest-palette in src/review/api/v1/themes.py — looks up title/artist via load_library() (same pattern as export.py), reads genre/occasion from the request body (the dialog's current in-progress values, not necessarily the song's saved genre). Returns {"palette": [...]} or a graceful {"error": {"code": "ai_unavailable", ...}} (200, not 4xx — an expected outcome, not a request error).

New ollama_host / ollama_model keys in the existing flat ~/.xlight/settings.json store (src/settings.py, no code change needed, no schema version). No new settings UI screen in v1 — hand-edit the JSON file for now.

Frontend

Theme.tsx — button in the existing dialog

New suggesting: boolean on EditState; new handleSuggestPalette() in Theme (has song.song_id in scope); new “✨ Suggest with AI” button in EditDialog above the Palette textarea, disabled + “Suggesting…” while in flight (mirrors the existing Save button's saving pattern). On success replaces state.palette only — accent_palette is v1-out-of-scope, not validated this session. On failure, sets state.error without closing the dialog or discarding manual edits.

Alternatives considered

OptionRejected because
Auto-apply during generation (original scoping) Needs a whole fallback-on-failure design inside build_plan(), breaks pipeline determinism when enabled, and validated quality (decent but same-y) isn't strong enough to trust unattended. The manual editor already has a human review step built in.
Suggest accent_palette too Only the 4-color main palette prompt was actually tested this session — small follow-up, not bundled here.
format: "json" string instead of JSON Schema Proven unreliable this session — inconsistent wrapper keys, occasional garbage, vs. schema mode's 10/10 clean results.
Dedicated settings screen for Ollama config No existing settings-screen infrastructure to build on; hand-editing settings.json is sufficient for v1.

Network reachability by deployment mode

TargetConfidenceWhy
Tauri .exe
real end-user deployment		 High tauri.conf.json: "security": {"csp": null} — no CSP blocking outbound fetch(). The bundled backend is a PyInstaller sidecar running as a native Windows process on the same machine as the user's Ollama install — exactly the native-host-to-native-host path this session's live testing already exercised successfully. Not yet verified against the actual compiled .exe + sidecar (config-only inspection so far), but this is the path that actually matters for users.
Docker (xlight-dev)
dev-only		 Likely blocked Default-deny egress firewall (.devcontainer/init-firewall.sh, ipset-based domain allowlist). host.docker.internal is a Docker-internal address, not a resolvable public domain — doesn't fit the mechanism as-is. Would likely fail into the graceful "AI suggestion unavailable" path rather than crash anything. A developer-experience gap, not a user-facing blocker — end users get the .exe, not the devcontainer. Worth fixing for contributor convenience, but does not gate shipping.

Validation

  1. Unit: all failure modes mocked in test_ai_palette.py, no real network calls in the suite.
  2. Manual, native host (primary target): click the button against the real local Ollama instance, confirm population and graceful error display when Ollama is stopped.
  3. Manual, packaged .exe (before considering this "done" for real users): repeat against an actual built .exe + PyInstaller sidecar, confirming the config-level analysis above holds in the real packaged artifact.
  4. Dev-convenience only, not a ship blocker: check whether the xlight-dev firewall needs an allowlist fix so contributors don't hit a silent failure every time while developing this feature inside the container.
