OpenSpec design · corpus-recipe-song-variety

Design: song-seeded corpus-recipe variety

Make a prop family's primary/alt effect choice vary song to song, not just occurrence to occurrence within one song — piloted on minitree, where fresh mining data shows real vendor songs commit to genuinely different dominant looks, which today's fixed alternation pattern flattens into one identical rhythm for every song.

The problem

Every non-rotation family's alt-effect decision is (variation_seed // 2) % 2 == 1, where variation_seed = config.variation_seed (per-song) + section_index. Because the arithmetic is the same for every song, the pattern of primary/alt across a song's qualifying occurrences is identical for every song: occurrence 0 primary, occurrence 1 alt, occurrence 2 primary … This varies effect choice within a song but never varies it across songs — every generated song walks the same lockstep rhythm.

This isn't "which number is right" — it's confirmation that real songs each commit to their own dominant look. Averaging into one fixed winner (old approach) or one fixed alternation rhythm (current approach) both throw away that variety.

Approach

New field

PropFamilyRecipe.song_seeded_alt_share

tuple[int, int] | None = None — a (min, max) range, out of a fixed 8-slot pool, for how many of a song's qualifying occurrences use alt_effect_name. Default None preserves today's fixed parity for every family except the one that opts in.

Minitree: song_seeded_alt_share=(2, 6) — 25%–75% Shockwave share, centered on the ~50/50 mined aggregate, bounded so a song can never land on 0/8 or 8/8 (the exact "one effect the whole song" bug class already fixed elsewhere).

Mechanism

Per-song shuffle, reusing the mirror-overlay pattern

elif recipe.alt_effect_name is not None:
    if recipe.song_seeded_alt_share is not None and occurrence_index is not None:
        pool_size = 8
        alt_min, alt_max = recipe.song_seeded_alt_share
        rng = random.Random(f"song_alt_share:{song_seed}:{recipe.family}:{group.name}")
        alt_count = rng.randint(alt_min, alt_max)
        seq = [True] * alt_count + [False] * (pool_size - alt_count)
        rng.shuffle(seq)
        use_alt = seq[occurrence_index % pool_size]
    else:
        use_alt = (variation_seed // 2) % 2 == 1
    if use_alt:
        effect_name = recipe.alt_effect_name
        ...  # existing alt_rotation_effect_name / bounce logic, unchanged

Same idea already shipped for megatree's mirror overlay (2026-07-23, random.Random(f"mirror_overlay:{variation_seed}").sample(...)) — corrected here to key off a genuinely song-constant seed instead of the per-section one (see Historical echoes).

New parameter

song_seed — recovered, not newly stored

variation_seed = config.variation_seed (per-song base) + section_index is already the documented formula. song_seed is just assignment.variation_seed - assignment.section_index, computed at the 4 call sites in effect_placer.py — no new field on SectionAssignment, no config plumbing.

Alternatives considered

OptionRejected because
Fully switch minitree to motion_rotation (megatree/matrix's mechanism) The per-beat-block bounce reroll (2026-07-28 fix for "shockwaves don't change for 65s") is wired to the alt_effect_name branch specifically, not motion_rotation. Switching silently drops that fix.
Unweighted 50/50 coin flip per occurrence, no per-song bias Doesn't match the data — real songs commit to a dominant look with occasional variation, they don't alternate randomly. Would just be a differently-random version of "every song looks statistically identical."
Unbounded per-song share (0–8 of 8) Lets a song land on 0/8 or 8/8 — literally the monotony bug this change exists to fix.
Apply to all primary/alt families in one change Explicit user direction: pilot on minitree, which has concrete new data showing the problem, before generalizing.

Regression surface

  • PropFamilyRecipe — new field, default None. Only constructed in CORPUS_RECIPES; every family except minitree stays on the old codepath, bit-for-bit unchanged.
  • _place_corpus_recipe — private, 4 call sites, all updated together; no test calls it with bare positional args that would break from an added keyword-only parameter.
  • Existing minitree parity tests — test_minitree_alternate_is_shockwave_burst and test_minitree_bounce_occurrence_implodes currently assume the old parity rule picks Shockwave at corpus_occurrence=1; they need a pinned song_seed once the selection rule changes. Flagged so it isn't missed.
  • Golden/microscope baselines — minitree output changes by design; re-run microscope panel, review, re-promote only after microscope sensitivity passes.

Historical echoes

  • 2026-07-28 Shockwave bounce reroll — a long occurrence must keep varying, not freeze on one look. Preserved: this change only touches which occurrences pick alt_effect_name, not what happens once they do.
  • bug-182 / "variation_seed is the global section index" — raw section-index arithmetic aliases with regular section strides. song_seed is deliberately the song-constant component, not the raw per-section value, to avoid this recurring in a new form.
  • 2026-07-23 mirror-overlay shuffle — direct precedent for "shuffle a pool's walk order per song." Noted deviation: that existing mechanism keys off the raw per-section variation_seed, so it likely reshuffles across a song's multiple qualifying sections rather than staying stable — not fixed here (out of scope, different family), but deliberately not copied into this new mechanism.
  • tier-layering-policy / prior "one effect the whole song" fixes — recurring pattern across several past incidents (arch direction rotation, Single Strand render-style freeze, Shockwave bounce reroll). The (2, 6)-of-8 bound directly applies that lesson: never let a per-song draw reach the 0-variety extremes.
  • No matching buglog/cerebrum entries found for song_seeded_alt_share or cross-song-variety regressions beyond the above.

Validation

  1. Unit: new song-seed-variety tests (different song_seed → different but bounded alt-shares); updated parity tests; full pytest tests/unit/test_generator -v.
  2. Regenerate several new corpus songs (Believer, Magic, Sounding Joy, Uptown Funk) plus a couple from the original 12-song corpus; confirm minitree's Shockwave/SingleStrand ratio visibly differs song to song, never 100% one effect.
  3. xlight-evaluate microscope panel against current baselines; review the diff, re-run microscope sensitivity, re-promote only after it passes.

Out of scope

Generalizing song_seeded_alt_share to other primary/alt families (arch, cane, snowflake, horizontal, vertical, spiraltree, star) — deliberately deferred until the minitree pilot is validated against real rendered output. Also out of scope: any change to motion_rotation-based families (megatree, matrix), which already have their own rotation/shuffle mechanisms and are not part of this "fixed parity" problem.
