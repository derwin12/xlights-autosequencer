OpenSpec design · plan-variety-validator

Design: pre-write plan variety validator

Catch the recurring “one effect the whole song” bug class inside the generation pipeline, before a .xsq is written — complementing xlight-evaluate microscope, which only runs after the fact, well after generation, and only when a developer remembers to run it.

Why now

Prompted by reviewing a comparable open-source xLights sequencer (Sacx83/sequencer), which validates and scores its generated plan before writing the sequence file. We only check quality after. This specific failure shape — one effect monopolizing an entire song for a group that's supposed to show two — has recurred multiple times, always caught by a human noticing a bad render:

IncidentRoot cause
bug-197Arch direction/size locked for a whole song
2026-07-28 bounce rerollBounce computed once per occurrence, not per beat-block — a 65s occurrence froze on one look
Mirror-overlay aliasing(seed // 2) % pool_len aliased with section stride — Lightning unreachable on a real song
This session’s minitree findingFixed parity meant every song showed the same alternation rhythm, not zero variety but identical variety

V1 check

corpus_recipe_monotony — the one proven failure shape

For every tier-6/8 group matched by recipe_for_group() whose recipe sets alt_effect_name: collect every placement across the whole song's SectionAssignment.group_effects[group_name] whose effect_name is either recipe.effect_name or recipe.alt_effect_name (ignores On-mask/secondary/overlay layers deliberately — this is about the primary/alt choice only). If the group has ≥2 qualifying occurrences and 100% share one effect, emit a warning.

Deliberately narrow: one specific, already-proven bug shape, not a general variety-score heuristic that would need its own calibration before being trustworthy. motion_rotation families (megatree, matrix) are out of scope for V1 — they already have their own reachability-guaranteed occurrence counter and would need a differently-shaped check.

Wiring

Informational only — logged, not blocking

build_plan() calls validate_plan() right before constructing the returned SequencePlan, storing the result in a new warnings: list[PlanWarning] field (default []) and logging each one via the existing module logger. No caller is required to change — purely additive. Blocking generation, UI surfacing, and gate integration are explicit follow-ups, not part of this change: let the check run silently-logged first and confirm no false positives before anything depends on it.

Alternatives considered

OptionRejected because
General variety-score / entropy heuristic across the whole plan Needs calibration against real output before trustworthy — risk of flagging legitimately low-variety songs (e.g. a family that only qualifies once). The narrow check needs no calibration: 100% one effect across 2+ occurrences is unambiguous.
Block generation on a warning Could break existing consumers on a false positive. Let it run informationally first.
Extend to motion_rotation families now Different mechanism, different failure shape (aliasing/reachability, not fixed parity) — needs its own check design, not a copy-paste of this one.
Separate post-hoc script (like microscope) instead of inside build_plan() Defeats the purpose — catching this before a .xsq reaches disk, at zero extra cost since the data already exists in assignments/groups at that point.

Regression surface

  • SequencePlan — new field, default []. Constructed only in plan.py's single return SequencePlan(...) site plus test fixtures using keyword args — nothing breaks.
  • build_plan() — verified single return point, no signature change, no new required parameter.
  • No existing test changes behavior: the field defaults empty and nothing reads it outside the new test file.

Historical echoes

  • bug-197 / 2026-07-28 bounce reroll / mirror-overlay aliasing — all the same underlying problem family (a selection mechanism silently collapsing to one branch), different mechanisms. This check targets the simplest, most direct form of it.
  • This session's minitree song-seeded-variety change — a natural complement: that change fixed cross-song sameness for one family; this validator is a safety net catching within-song monotony across any family with alt_effect_name set, including future recipe changes that might reintroduce it.
  • No matching buglog/cerebrum entries found for plan_validator or pre-write validation gates beyond the above.

Validation

  1. Unit: new test_plan_validator.py; full pytest tests/unit/test_generator -v.
  2. Construct a deliberately-monotone plan and confirm it's flagged; confirm the already-fixed arch/cane/etc. recipes (genuine two-effect variety via the old parity mechanism) do NOT spuriously flag.
  3. Run a real generation and confirm plan.warnings populates as expected, with zero warnings on a healthy song.

Out of scope (explicit follow-ups)

Blocking generation on a warning; surfacing warnings in the review UI; failing the acceptance gate on a warning; extending the check to motion_rotation families. All deferred until the V1 check has run informationally for a while with no false positives.
